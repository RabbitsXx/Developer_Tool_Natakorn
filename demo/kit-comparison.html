Same three tasks, with and without the VibeCoder Kit

Every number below comes from a real recorded trial: a job-tracking API built from zero, three tasks end-to-end (bootstrap → code → verify), documented in docs/AUDIT.md and tagged v1.0.0. The "without" column is what the same work looks like with a bare agent and no operating kit.

Task 1 — Build an HTTP API (create / fetch / list jobs)

The kit's api pack forces the contract to be written before handlers, and bans "tests pass" as evidence.

Without tool Happy path shipped

  • Endpoints coded first, contract invented by whatever the handler returned — error shapes drift per route
  • Verified by "it runs" + a successful build
  • 200-with-error-payload and leaked stack traces survive to production
  • No replayable request collection; next session re-discovers the API by reading source
Verification actually run: 0 real requests · negative paths: none

With tool Contract-first, request-proven

  • Route table + error envelope fixed in docs/api-contract.md before code
  • Live server request matrix: 401 unauthenticated, 403 viewer-on-write, 422 invalid type, 413, 415, 405 + Allow
  • Replayable collection committed (docs/requests.http)
  • 15/15 verify checks, each with expected vs observed status
15/15 checks · 31 tests · pack context loaded: ~5,900 tokens (not the whole kit)

Task 2 — Schema change (v1 → v2, new fields)

The kit's data-layer pack: "never claim a migration succeeded because the app still builds."

Without tool Edit the file, hope

  • Fields added straight to the record shape; old data read with the new code — or crashes, or silently misreads
  • No rollback path, no version marker, no way back
  • "Verified" because the build passed
Rollback executed: never · idempotence: unknown

With tool Migration with receipts

  • Versioned migration chain; store refuses a v1 log and names the command to run
  • Live drill on the app's own data: --up backfilled 3/3 → repeat --up applied 0 (idempotent)
  • --down executed and byte-checked: exact v1 records restored
  • Constraint negatives tested: duplicate key rejected, negative counter rejected
Rollback: executed & verified · 10 data-layer tests · ~2,600 pack tokens loaded

Task 3 — Fix the bug the packs found

The kit's testing pack: regression first, watch it fail for the stated reason, then fix.

Without tool Patch and move on

  • Race "fixed" by adding a check somewhere else — same class of bug ships again later
  • No test; the fix's correctness rests on the author's confidence
  • Report: "should be fixed now"

With tool Failing-first, pinned forever

  • Test written first, confirmed failing 3/3 runs for the stated reason (all 201s)
  • Fix: serialized create + store-level uniqueness; test green 3/3 runs
  • Named regression test prevents the whole class; release pack preflight run with scope honestly limited (no deploy target — stated in the record)
Suite: 42/42 · verify: 15/15 · evidence table printed by the project's own npm run verify

Verdict

Same agent, same model, same three tasks. The difference is not intelligence — it's that the kit replaces "the agent's habits" with rules that produce evidence: contracts written first, checks that must actually run, migrations that must roll back, bugs that must be pinned failing-first. The concrete proof: the packs' own rules surfaced a real concurrency bug that a happy-path session would have shipped.

What the kit does not claim

  • The command gate is a gate + audit trail, not an OS sandbox — an agent that bypasses it can still run raw shell.
  • Token figures are bytes/4 estimates, not measured tokenizer counts.
  • Release evidence here is local preflight only; no deploy target existed to verify against.
